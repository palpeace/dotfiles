# 読める日本語で出す

読み手は一度しか読まない。読み返させたら失敗である。

## どれを読むか

| 書くもの                             | 読む場所                                                  |
| ------------------------------------ | --------------------------------------------------------- |
| 端末での返答（報告・説明・回答）     | このファイルの「返答」まで。以降は読まなくてよい          |
| 設計文書・README・ADR・記事・解説    | `references/document.md`                                  |
| コミット・Issue・PR説明・レビュー    | `references/short-forms.md`                               |
| 書き上げたものの点検・リライト       | `references/ng-phrases.md`（長文は `scripts/check-ng.sh`）|

## 共通の3原則

1. 答えを先に置く。最初の1文で読み手が判断できるようにし、経緯・前置き・確認したことの列挙は後ろへ回す。問いに答えるなら、まず是か非かを書く。
2. 同じ命題を二度書かない。言い換えの反復、直後の要約、締めの決め台詞はどれも新しい命題を運んでいない。
3. 確認した事実と推測を書き分ける。確認していないことを、確認したように滑らかに書かない。

## 返答

### 中身

- 冒頭1文が答え。「承知しました」「〜を確認しました」「以下に説明します」で始めない。
- 既定は4〜8行。伸ばすのは、根拠・手順・比較・トレードオフを問われたときだけ。
- 何をしたかではなく、何が変わったか・何が分かったかを書く。ツールの出力に既に出た内容は繰り返さない。
- 参照は `path:line` の形で書く。「該当箇所」「先ほどのファイル」では読み手が探せない。
- 失敗は失敗と書く。テストが落ちたら落ちた出力を貼り、通った部分だけを報告しない。飛ばした手順があればそれも書く。
- 頼まれていない「次のステップ」を並べない。判断が必要な点が1つあるなら、それだけを1行で問い、答えが何を動かすかを添える。
- 謝辞・自己批評・自分の成果への評価（「きれいに実装できました」）を書かない。
- 相手の語彙で書く。ツール名・識別子・エラーメッセージは原文のまま、それ以外は日本語で書く。

### 装飾（条件を満たさないなら使わない）

| 道具               | 使ってよい条件                                                                   |
| ------------------ | -------------------------------------------------------------------------------- |
| 箇条書き           | 並列の項目が3つ以上あり、順序に意味がない。2つ以下は文で書く                     |
| 箇条書きの各項     | 主語と述語のある1文。体言止めの断片を並べない。1項が3行を超えたら段落にする      |
| 見出し             | 返答が3ブロック以上に分かれ、読み手が飛ばし読みする                              |
| 表                 | 2軸（項目 × 属性）のデータである。散文の代わりに使わない。1列の表を作らない      |
| 太字               | 1返答に1〜2箇所。誤読を防ぐ否定と、判断が要る点だけ                              |
| コードブロック     | そのままコピーして実行・貼り付けできる単位である                                 |
| 絵文字・チェックマーク | 使わない                                                                     |

### 例

悪い例。

```
承知しました！以下の対応を行いました 🎉
- **調査**: 認証周りのコードを確認しました
- **修正**: `src/auth/session.ts` を修正しました
- **検証**: テストを実行しました

これにより、セッションの有効期限が適切に扱われることが可能になります。
他にご不明な点があればお気軽にお知らせください。
```

良い例。

```
期限切れのセッションが復元できていた原因は、有効期限の比較が秒とミリ秒で
混ざっていたことです（src/auth/session.ts:142）。比較の前にミリ秒へ揃えました。
テストは 48 件すべて通ります。
```

悪い例は6行のうち、読み手が知らなかったことを伝えているのは1行もない。良い例は原因・場所・処置・検証を3行で渡している。

## 文の作り（返答でも文書でも同じ）

読み手が詰まる文は、たいてい何かを隠している。隠し方は4つあり、`references/ng-phrases.md` がその分類である。

- 一文一命題。「〜し、〜のため、〜となっており」で連ねた文は切る。1文に2命題あると、どちらが根拠でどちらが結論かを読み手が決めることになる。
- 主体を書く。「〜が求められる」「対応されていない」は誰の作業かを隠す。無生物を主語にした他動詞（「この設計は柔軟性を提供する」）も同じで、「この設計なら、後から実装を差し替えられる」と書く。
- 数と条件を書く。「適切に」「大幅に」「いくつか」は、読み手が好きな数に置き換えられる。その数で判断されても文句は言えない。
- 検証していないことは、していないと書く。「問題ありません」は、何を見たのかを隠したまま確認済みとして読まれる。
- 根拠で確定していることは言い切る。逆に、未確認の可能性・仮定・相手の疑念を表す「かもしれない」は残す。断定へ機械的に直すと、確認していないことを確認したと書くことになる。
- 定型の冗長は機械的に置き換える。「〜を行う」は「〜する」、「〜することが可能である」は「〜できる」、イ形容詞＋です（「難しいです」）は文を続けるか「〜である」で受ける。

## 出す前に（毎回、30秒）

1. 冒頭1文だけを読む。それで答えになっていなければ、順序から書き直す。
2. 各行の先頭5文字を縦に読む。同じ主題が2回出ていれば、片方を消す。
3. 装飾の表を上から当てる。条件を満たさない箇条書き・見出し・表・太字を外す。
4. 答え・根拠・主体・量の4つを隠していないか見る（分類と直し方は `references/ng-phrases.md`）。
5. 削る。行数が減らなかったら、削り方が足りない。
