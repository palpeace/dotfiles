# 短い形の規範（コミット・Issue・PR・レビュー）

短い形は、後から検索して読まれる。書いた時点の文脈は残らないので、それ単独で意味が取れるようにする。

## コミットメッセージ

- 1行目は `feat:` `fix:` `docs:` `refactor:` `test:` `chore:` の接頭辞＋変更の結果。50字前後を目安にする。
- 何をしたかではなく、何が変わったかを書く。「session.ts を修正」ではなく「期限切れセッションが復元される不具合を直す」。
- 本文（2行目以降）に書くのは「なぜ」だけ。差分を読めば分かることを繰り返さない。
- 1コミットに1つの変更。接頭辞が2つ浮かぶなら、コミットを割る。
- 動機が外部にあるなら参照を1つ置く（Issue番号、裁定の日付）。

例。

```
fix: 期限切れセッションが復元される不具合を直す

有効期限の比較で、保存側が秒・判定側がミリ秒だった。
判定側へ揃える方を選んだのは、保存形式が外部APIの契約だから。
```

## Issue

- タイトルは達成状態か、観測された問題。作業名（「〜の調査」）にしない。
- 本文は3つで足りる。いま何が起きているか、どうなっていれば終わりか、その判定を誰がどう行うか。
- 終わりの条件は、観測できる形で書く。「改善する」ではなく「同じ入力で再現しない」。
- 分からないことは分からないと書き、調べる前の仮説と区別する。

## PR説明

- 冒頭1文で、この変更で何が変わるかを書く。
- 検証したことと、していないことを分ける。手で確認しただけなら、そう書く。
- 影響範囲（触っていないが挙動が変わる箇所）を挙げる。無いなら「無い」と書く。
- 差分を読めば分かる変更点の列挙で説明を埋めない。読み手が欲しいのは、なぜその設計にしたかである。

## レビューコメント

- 指摘は、問題・根拠・提案の3つで書く。提案の無い指摘は、相手の手を止めるだけになる。
- 好みと不具合を区別して書く。好みなら好みと明示し、通らなくても構わないと添える。
- 「〜すべき」ではなく「〜だと、Xのときに壊れる」と、壊れる条件で書く。
